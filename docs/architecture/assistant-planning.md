# Режимы планирования

Ветка сравнивает три способа получить одно и то же проверяемое предложение. Основной режим остаётся `DIRECT`; внешние HTTP-контракты, карточки предложений, политика подтверждения и применение действий не меняются.

| Режим | Что получает модель | Что возвращает |
| --- | --- | --- |
| DIRECT | Контекст до 80 задач и обычные инструменты | propose_actions, поиск с возможным вторым проходом, отказ |
| BATCH_PLAN | Правила, группы и схема декларативного плана | Шаги с фильтром задач и действием, уточнение или отказ |
| CODE_MODE | Правила и ограниченный JavaScript API | Код, который читает задачи и возвращает план |

`propose_actions` в основном алгоритме уже пакетный. Новый JSON-режим отличается серверными выборками: модель описывает критерий, а не перечисляет заранее известные ярлыки каждой задачи. В Code Mode промежуточные результаты остаются в песочнице; модель может использовать условия и вычисления. Для обоих режимов начальное окно задач остаётся на сервере для общей защиты от дублей, но не передаётся модели.

Выборка выполняется только для текущего пользователя, скрывает удалённые задачи и по умолчанию включает активные. Фильтры: подстрока названия/описания, точное имя группы, статус, приоритет, просрочка, полуоткрытый интервал срока. Поиск возвращает не более 20 задач, а 21-я служит признаком превышения лимита. Нельзя молча применить план к первым двадцати из большего числа. Если совпадений несколько, требуется явный `all=true`; для одиночной команды возвращается уточнение. Нулевой результат JSON-шага требует уточнения; код может обработать пустой массив условием.

Результат обоих исполнителей проходит существующие ToolCallParser, ActionValidator, DuplicateGuard и TitleChangeGuard, затем сохраняется как обычное предложение. Перед применением повторно проверяются владение и состояние задач. Исполнитель ничего не записывает; автоприменение новых задач остаётся политикой существующей точки быстрого добавления. Ярлыки, которых программа не получила из выборки, запрещены.

## Переключение

```bash
ASSISTANT_PLANNING_MODE=DIRECT
ASSISTANT_PLANNING_MODE=BATCH_PLAN
ASSISTANT_PLANNING_MODE=CODE_MODE
```

Переменная передаётся ядру через Compose. При смене режима достаточно пересоздать ядро только своего проекта. При первом запуске новой версии нужно пересобрать его образ. На хосте для Code Mode нужны Node >=16 и `npm ci --ignore-scripts` в `code-runtime/`; путь можно указать явно через `CODE_MODE_RUNNER`. В Docker зависимости уже входят в образ. При обычном DIRECT процесс Node не запускается.

## Проверки и сравнение

`PlanningModesIntegrationTest` использует отдельный PostgreSQL и фиксированные ответы модели. Проверяются выборки за пределами начального окна, изоляция пользователей, лимиты, неоднозначность, управляющие ответы и отсутствие записи в БД. `code-runtime/test` проверяет исполнение настоящего JavaScript, недоступность Node/сети/импортов, память, бесконечный цикл и лимиты вывода/вызовов.

Офлайн-прогон пишет `core-service/app/build/reports/planning-offline.json`: размер сериализованного запроса в байтах, проходы и время локального исполнения на одинаковых синтетических данных. Байты не являются токенами, а фиксированные ответы не измеряют качество понимания естественного языка. Для вывода о стоимости и качестве нужен отдельный согласованный прогон на реальной модели с её usage-метриками, учётом неудач и исправлений.

Прямые вызовы остаются контрольным вариантом. Ни один новый режим не включается автоматически по результатам теста. Code Mode не отменяет стоимость чтений БД и добавляет запуск процесса; при небольшом числе простых команд декларативный режим может оказаться быстрее.

## Замер Groq, 8 ноября 2026

Модель `openai/gpt-oss-120b`, temperature 0.1. Шесть синтетических сценариев: создание со сроком, завершение задачи за пределами окна, перенос двух просроченных задач группы, неоднозначный отчёт, напоминание и благодарность. У тестового пользователя 89 задач; реальные аккаунты не использовались. Планирование ничего не применяло к задачам.

Первый прогон, до исправления подсказки об отсутствующем окне:

| Режим | Верно | Входные токены, сумма | Выходные токены, сумма | Среднее время |
| --- | --- | --- | --- | --- |
| DIRECT | 2/6 | 26 748 | 1 979 | 1 149 мс |
| BATCH_PLAN | 2/6 | 16 380 | 1 796 | 869 мс |
| CODE_MODE | 3/6 | 15 812 | 2 763 | 1 506 мс |

Вход уменьшился примерно на 39% и 41%, но Code Mode потратил больше выходных токенов и времени. Это измерение расхода всей попытки, включая исправления, а не стоимости успешной операции. Низкое качество всех вариантов не позволяет выбрать победителя. Сценарий создания и благодарность прошли у всех; остальные ошибки нельзя вычёркивать из сравнения.

Замер выявил неверную подсказку новых режимов: непереданный список описывался как отсутствие активных задач. После исправления JSON успешно завершил скрытую задачу и перенёс обе просроченные задачи группы (2/2 реально запущенных сценариев; 5 565 входных и 607 выходных токенов). Code Mode в двух сценариях возвращал целую `async`-функцию вместо тела; по одной попытке исправления не помогло. Эти четыре вызова израсходовали 9 584 входных и 2 171 выходной токен, а сами сценарии закончились без действий.

Исполнитель теперь принимает оба формата. Две полученные программы сохранены как синтетические регрессионные фикстуры и повторно исполняются с настоящей изолированной БД. Такая проверка исправляет найденную несовместимость, но не является повторным живым измерением качества. Напоминания после правки повторно не проверялись: общий предел 25 HTTP-запросов исчерпан (19 в первом прогоне и 6 во втором). Два отказа `BUDGET_OR_APPROVAL` во втором отчёте означают локальный запрет отправки, а не ошибку Groq; сетевых ошибок API не было.

Вывод: оба варианта доступны для дальнейшего эксперимента, DIRECT остаётся основным. Для включения другого режима нужен больший одинаковый набор команд с повторными прогонами, проверкой ошибочных массовых действий и неоднозначности. Тест из шести фраз не доказывает надёжность на реальных данных. После правок полный сравнительный прогон не проводился; смешивать результаты разных версий в одну оценку качества нельзя.

Живой тест запускается отдельно и только с явным opt-in:

```bash
PLANNING_LIVE_APPROVED=true PLANNING_LIVE_CALL_LIMIT=25 \
  ./gradlew :core-service:app:liveTest --tests '*PlanningComparisonLiveTest'
```

`GROQ_API_KEY` должен быть задан окружением; ключ не записывается в отчёты. Лимит действует на один запуск процесса: при повторном запуске нужно вручную учесть уже потраченные запросы. `PLANNING_LIVE_FOLLOWUP=true` оставляет три проблемных сценария и два экспериментальных режима; лимит включает исправления, поэтому поздние сценарии могут не отправиться. Отчёты лежат в `core-service/app/build/reports/planning-comparison.json` и `planning-followup.json`. Обычный `test` не вызывает Groq.

Реализован сам [паттерн Code Mode](https://developers.cloudflare.com/agents/tools/codemode/), без зависимости от облачного исполнения Cloudflare. Для локальной песочницы используется [QuickJS/WASM](https://github.com/justjake/quickjs-emscripten), с ограничениями процесса и проверками ядра поверх него. Это не отдельный контейнер на каждую программу и не абсолютная защита от уязвимостей движка. Node-процесс работает с правами процесса ядра; гостевой JavaScript видит только предоставленный API. Предел памяти QuickJS не равен пределу RSS процесса.

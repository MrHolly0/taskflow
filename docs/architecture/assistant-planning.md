# Режимы планирования

По умолчанию используется BATCH_PLAN — декларативный JSON-план. DIRECT остаётся для явного отката, CODE_MODE — экспериментальным режимом. Режим выбирается через ASSISTANT_PLANNING_MODE; внешние HTTP-контракты предложений и интерфейс подтверждения не меняются.

| Режим | Вход модели | Выход модели |
| --- | --- | --- |
| DIRECT | Исходные инструкции, до 80 задач и обычные инструменты | propose_actions, поиск с возможным вторым проходом, отказ |
| BATCH_PLAN | Отдельные инструкции и до 12 активных кандидатов | JSON-объект с шагами, уточнением или отказом |
| CODE_MODE | Те же кандидаты и ограниченный JavaScript API | Один вызов execute_code с программой |

propose_actions в DIRECT уже пакетный. JSON-план отличается серверным разрешением выборок, а Code Mode позволяет добавлять условия и вычисления без промежуточной передачи найденных задач модели.

## Контекст и выборки

Начальное окно до 80 задач остаётся на сервере для общей защиты от дублей. Модели передаются до 12 активных кандидатов: ref, title, status, priority и при наличии group, deadline, plannedDate, estimateMinutes. В JSON при неполном списке сервер сначала ищет релевантные задачи по словам исходной реплики: до шести результатов объединяются с обычным окном, общий предел остаётся равным двенадцати. Code Mode сохраняет исходное окно без этого поиска. UUID и идентификатор пользователя программе не выдаются.

У JSON-шага select находится рядом с action. Ссылка select.ref разрешается только среди выданных кандидатов или результатов поиска. Для остальных задач поддерживаются query, group, status, priority, overdue, deadlineFrom и deadlineBefore. В JSON поиск сначала проверяет буквальное совпадение, затем все нормализованные русские слова. Формы слов обрабатываются PostgreSQL, для нескольких производных от действий используется общий префикс. Это не произвольное исправление опечаток. Частичное совпадение слов не считается найденной целью: до трёх возможных кандидатов передаются модели только при исправлении NOT_FOUND. В Code Mode query остаётся буквальной подстрокой. Все чтения ограничены текущим пользователем; удалённые задачи скрыты, по умолчанию выбираются активные. Владение повторно ограничивается и при загрузке выбранных строк из БД.

Без all=true допускается не более одного совпадения; несколько требуют уточнения. Для явной массовой команды используется all=true. В JSON сервер дополнительно проверяет наличие массового намерения в исходной реплике. При all=true учитываются и буквальные, и совпадающие по формам слов результаты; приоритет точного написания не должен скрыть часть массовой выборки. Выборка читает 21 идентификатор: двадцать результатов и признак превышения лимита. При превышении нельзя молча обработать первую часть списка. Ошибка небезопасной выборки отклоняет весь план, включая уже подготовленные шаги.

Лимиты: восемь поисковых выборок, двадцать шагов и двадцать итоговых действий. Разрешение известного ref не обращается к БД и не расходует лимит поисков.

## Исполнение

JSON-режим использует отдельные инструкции с явным поисковым select для задач за пределами кандидатов и примерами взаимоисключающих вариантов. Явное указание пользователем новой группы допустимо; автоматическое придумывание группы запрещено. Поиск выполняет сервер после получения JSON: модели не нужно сначала вызывать инструмент и получать полные результаты.

JSON-режим использует response_format=json_object без function calling. Это обеспечивает синтаксический JSON, но не заменяет проверку структуры и смысла. Ошибки плана проверяет ядро.

Code Mode получает api.tasks (кандидаты), api.now (строка ISO8601) и api.findTasks(selector). Принимается тело async-функции или выражение async () => { ... }. Программа возвращает actions, clarification либо decline.

Оба режима используют прежние ToolCallParser, ActionValidator, DuplicateGuard и TitleChangeGuard. У явных планов нет запасного создания задачи из сырой команды при ошибке проверки. Предложенные моделью действия проходят общий валидатор. Явные взаимоисключающие варианты с ambiguous_reason сохраняются. В JSON сервер также распознаёт узкий случай короткой ссылки без параметров и факта выполнения: при единственной подходящей задаче формируются два взаимоисключающих варианта — существующее и новое дело. При нескольких целях требуется уточнение. Пустой update и перенос без нового срока не выдаются за полезный вариант. DIRECT продолжает использовать исходный алгоритм.

JSON допускает reminder_before_deadline_minutes: сервер вычисляет момент от реального deadline найденной задачи или от нового срока в том же плане. Порядок шагов модели не меняет базу вычисления. При применении изменения срока и названия идут перед отдельными напоминаниями, чтобы обновление задачи не отменило только что созданное уведомление. new_deadline_time сохраняет календарный день задачи в зоне пользователя. При одном временном поле и однозначном относительном дне сервер подстраховывает отсчёт от текущего дня; смешанные даты и неизвестные формулировки не переписываются. Единственный явно названный час напоминания без дня означает ближайшее будущее наступление часа; неоднозначные переходы часового пояса требуют уточнения.

После проверки результат сохраняется как обычное предложение. Взаимоисключающее предложение допускает не более одного принятого действия; это проверяется и при выборе варианта, и перед применением. Владение и состояние задач повторно проверяются перед применением. Планировщик и песочница ничего не записывают в задачи; автоприменение новых задач остаётся политикой существующего быстрого добавления.

## Генерация и ошибки

Для новых режимов по умолчанию выбран low reasoning effort. При единственной попытке исправления low повышается до medium. Это часть экспериментальной конфигурации, а не свойство JSON или Code Mode. DIRECT не получает новых настроек и сохраняет исходный запрос к поставщику.

ASSISTANT_EXPERIMENTAL_REASONING_EFFORT принимает low, medium, high или default. Последний вариант оставляет интенсивность на усмотрение поставщика. Необязательный параметр передаётся только поддерживаемым GPT-OSS-моделям. Для Code Mode задан единственный обязательный инструмент; JSON-режим инструментов поставщику не отправляет.

Исправление допускается один раз при ошибке формата или программы. В JSON-режиме та же ограниченная попытка используется и при отклонении полей общим валидатором или неизвестной ссылке. Проверка формата, обязательных полей и выборок атомарна для всего JSON-плана: если исправление не помогло, корректная часть не выдаётся как полный результат команды. Сохраняется узкое прежнее исключение TitleChangeGuard: запрет переименования без полного текущего названия оставляет остальные корректные действия с видимым предупреждением. Если полезных действий не осталось, требуется уточнение. Ошибка предыдущей отклонённой выборки сбрасывается только перед исправлением; общий лимит поисков не обнуляется. Code Mode сохраняет прежний порядок проверки. Токены и время обеих попыток суммируются. Неоднозначность и превышение объёма выборки не превращаются в создание задачи из сырой команды. При недоступности модели планировщик возвращает llmFailed без действий. Сервис ассистента сохраняет прежнюю общую политику деградации: исходный текст можно сохранить как задачу с признаком DEGRADED. Это поведение существует вне планировщика и не является успешной интерпретацией команды.

## Песочница

Исполнение происходит в новом Node-процессе и новом QuickJS/WASM runtime на каждую программу. Node eval/vm не используется. Гостевой код не получает файловую систему, сеть, импорты, process, console или ключи API. Окружение дочернего процесса очищено.

Ограничения: исходник 16 КиБ, память QuickJS 16 МиБ, стек 256 КиБ, до одной секунды с момента запуска VM и трёх секунд на весь процесс. До 1000 заданий очереди promise, восьми вызовов API и 32768 символов результата. Ядро запускает один исполнитель одновременно; переполнение не создаёт неограниченную очередь. Node дополнительно ограничен кучей 64 МиБ; это не лимит RSS процесса. Общий предел памяти задаётся контейнером ядра.

Это реализация [паттерна Code Mode](https://developers.cloudflare.com/agents/tools/codemode/) на [QuickJS/WASM](https://github.com/justjake/quickjs-emscripten), без облачного исполнения Cloudflare. Исполнитель работает с правами процесса ядра; отсутствие гостевого доступа к ресурсам не является гарантией от уязвимостей самого движка.

## Запуск

```bash
ASSISTANT_PLANNING_MODE=DIRECT
ASSISTANT_PLANNING_MODE=BATCH_PLAN
ASSISTANT_PLANNING_MODE=CODE_MODE
```

При первом запуске новой версии нужно собрать образы core-service и nlp-worker. Liquibase применяет миграцию 044 с GIN-индексом русскоязычного поиска; данные задач не переписываются. Новые необязательные поля внутреннего запроса понимают оба сервиса. В Docker Node и зависимости QuickJS уже входят в образ; при DIRECT и BATCH_PLAN процесс Node не запускается. На хосте Node и npm ci --ignore-scripts в code-runtime нужны только для CODE_MODE.

## Проверки и воспроизведение

Обычный Gradle test не вызывает Groq. PlanningModesIntegrationTest проверяет реальные выборки на отдельном PostgreSQL, изоляцию пользователей, выданные ссылки, лимиты, управляющие ответы, исправление программы, отсутствие записи в задачи и отсутствие лишних альтернатив у отмены. Node-тесты проверяют выполнение настоящего JavaScript, недоступность ресурсов хоста, бесконечный цикл, память, пределы вывода и вызовов.

Сравнение использует прежний набор из 150 реплик и прежний ActionMatcher. Перед каждым случаем для каждого режима создаётся новый тестовый пользователь с одинаковыми исходными задачами; порядок режимов ротируется. Исходная разметка не меняется, SHA-256 набора записывается в отчёт. У каждого режима сохраняются правильность, точность и полнота действий, входные и выходные токены, число HTTP-вызовов, исправления и задержка.

В старом оценщике час срока сравнивался без приведения часового пояса. Основной балл нормализует эквивалентные моменты времени; старый балл сохраняется отдельно как legacyCorrect. Это не исправление ожидаемых ответов. Некоторые ожидания самого старого набора неоднородны: например, в одной голосовой строке ожидаются исправленные слова, а в другой — исходные искажённые. Они оставлены как есть.

Живой прогон требует явного разрешения и расходует квоту Groq. Общий файловый счётчик не сбрасывается между запусками; ошибочные ответы тоже расходуют лимит. Ключ берётся из окружения или только из строки GROQ_API_KEY в infra/.env и в отчёты не попадает.

```bash
python3 scripts/compare-planning.py --allow-live --repeats 3 \
  --budget-limit 3000 --call-limit 1600 --pacing-ms 250 --run-name comparison

python3 scripts/summarize-planning.py \
  core-service/app/build/reports/planning-comparison.json \
  --output docs/architecture/planning-results.md
```

Датасет — локальный файл docs/vkr/dataset/nlp-dataset.json, не часть публичной сборки. Можно задать --dataset для другого синтетического набора. Инкрементальные результаты и диагностические ответы лежат в build/reports и не коммитятся. Сводка строится без новых обращений к модели и отказывается выдавать неполный прогон за законченный.

Сравнение оценивает полные реализации: одновременно меняются инструкции, объём контекста, транспорт ответа и настройка рассуждений. Для отдельного вывода о вкладе каждой техники потребуются дополнительные контролируемые проверки. Эти данные относятся к обработке готового текста; распознавание аудио не измеряется.

Итог трёх повторов исходного набора и дополнительные проверки: [результаты сравнения](planning-results.md).

Отдельный этап доработки JSON и повторная проверка: [результаты JSON](json-planning-results.md). Предыдущий отчёт сохраняет результаты прежней версии.

## Большие активные списки

Набор large-context содержит 14 сценариев для аккаунтов ровно со 100 и 200 задачами: создание с датами, создание с напоминанием, изменение видимых и скрытых задач, абсолютное и относительное напоминание, четыре действия в одной команде, перенос только просроченных дел группы, неоднозначность и превышение лимита массовой операции. Все задачи активны; набор не измеряет одновременную нагрузку пользователей.

PlanningLargeContextFixtureTest без модели проверяет все комбинации размера и сценария: количество задач, изоляцию аккаунтов и положение целей относительно окон 12/80. PlanningLargeContextScorerTest проверяет оценку с точностью до минуты и запрет зачёта технического сбоя как уточнения. Живой тест отдельно сверяет снимки задач, напоминаний и расписания уведомлений до и после планирования; предложения не применяются.

Для повторного запуска в рамках согласованного бюджета используется постоянный файл счётчика. Старые счётчики сохраняются. Пример отдельного этапа с пределом 360 HTTP-вызовов:

```bash
python3 scripts/compare-planning.py --allow-live --suite large-context \
  --task-counts 100,200 --repeats 3 --run-name large-final \
  --budget-file .gradle/planning-large-api-budget.json \
  --budget-limit 360 --call-limit 348 --pacing-ms 250

python3 scripts/summarize-large-planning.py \
  core-service/app/build/reports/planning-large-final.json \
  --output docs/architecture/planning-large-context-results.md \
  --csv docs/architecture/planning-large-context-measurements.csv
```

Для пилота можно ограничить --task-counts 100 и --case-ids complete-hidden,remind-relative-hidden,mixed,selection-limit. Его результаты хранятся отдельно и в итоговую точность не добавляются. Полный зачёт требует правильных типа и цели действия, временных полей и отсутствия лишних изменений. Новый оценщик строже прежнего ActionMatcher, поэтому проценты двух наборов напрямую не сопоставляются.

Итоговый прогон больших списков и разобранные ограничения: [результаты на 100 и 200 задачах](planning-large-context-results.md).


## Проверка полной замены

Перед переключением по умолчанию проверяются три условия на одинаковом исходном наборе: доля полностью правильных запросов, точность и полнота действий не ниже DIRECT; медиана и p95 задержки не выше. Токены учитываются вместе с исправлениями. Отдельные наборы больших списков проверяют точные цели, даты, напоминания, массовые операции и отсутствие записей при планировании.

Контрольный набор large-context/control содержит дополнительные формулировки, непривычные минутные отступы, ошибки диктовки и изменение нескольких приоритетов. После использования для исправлений это регрессионный набор, а не независимая итоговая выборка. Старый reminders-auto требует придумывать уведомления без явного времени и служебный флаг no_reminder_needed; он не соответствует действующим правилам планировщика и не входит в критерий замены. Его исходная разметка сохранена.


Результат подготовки полной замены и условия переключения: [итоговая проверка JSON](json-planning-replacement.md). Архивные отчёты выше относятся к прежним версиям и сохраняются без пересчёта.

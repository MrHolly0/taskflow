## Методика и ограничения

В каждом измерении создан отдельный синтетический аккаунт ровно со 100 или 200 активными задачами. Все исходные задачи находятся в TODO; это проверка длинного активного списка, а не воспроизведение распределения статусов реальных пользователей. Для каждого режима данные логически одинаковы; UUID различаются. Порядок режимов циклически меняется между сценариями.

DIRECT получает исходное окно до 80 задач и свой поиск. Экспериментальные режимы видят до 12 кандидатов и используют серверный поиск. Проверено, что цели hidden находятся дальше 80-й позиции, а visible — в первых 12. Есть похожие названия, две неоднозначные задачи, просроченные и будущие задачи одной группы, а также совпадающая задача чужого пользователя.

Тип действия и UUID цели проверяются взаимно однозначно. В метриках точности и полноты действий учитываются только тип и цель; правильные поля проверяются отдельно и обязательны для полного зачёта запроса. Дедлайн и reminder_at сравниваются по моменту времени с точностью до минуты. Пропуск требуемого действия считается ошибкой его времени. Лишние действия и непрошенные содержательные изменения полей не допускаются. Сценарий создания проверяет ключевые слова названий, а не полную семантическую эквивалентность текста.

Два контрольных сценария требуют уточнения без действий: неоднозначное название и выборка 21 задачи при лимите 20. Они входят в полную точность запросов; ожидаемых действий и временных полей в них нет. Технический сбой не засчитывается как успешное уточнение. Список действий свыше лимита нельзя принимать частично.

Проверяется фаза формирования предложений. Применение, доставка уведомлений и распознавание аудио не выполняются. Снимки строк задач и scheduled_notifications основного и чужого аккаунтов сверены до и после планирования. Совпадение снимков подтверждает отсутствие записей при планировании, но не проверяет последующее применение предложений.

Задержка включает чтение контекста, обращения к модели, исправления и песочницу; подготовка аккаунта и паузы между измерениями исключены. Отказы API остаются в знаменателях. В токены включён возвращённый usage всех попыток; расход отклонённых поставщиком обращений может быть неизвестен.

Это последовательное функциональное сравнение, а не нагрузочный тест ста пользователей. Три повтора одной формулировки не равны трём независимым пользовательским запросам. Набор небольшой и намеренно содержит трудные случаи. Проценты нельзя напрямую сопоставлять с прежними 150 репликами: различаются набор, состояние аккаунтов и более строгая проверка полей. Сравниваются реализации целиком, включая инструкции и настройки рассуждений; влияние формата отдельно не выделено.

## Разбор результата

В текущей реализации JSON получил 62/84 полностью правильных запросов, DIRECT — 21/84, Code Mode — 39/84. При 100 задачах JSON использовал на 48,5% меньше суммарных токенов, при 200 — на 52,0% меньше. Медиана и p95 ниже DIRECT при обоих размерах. Это результат полных реализаций на данном наборе, а не оценка всех команд продукта.

JSON выполнил все шесть проверок поиска скрытой задачи для завершения, отмены, абсолютного напоминания и смены группы, а также все шесть смешанных команд. В сценарии переноса скрытой задачи — 5/6. DIRECT в этих случаях часто сообщал об отсутствии существующей задачи или предлагал создание вместо изменения. Code Mode тоже нередко отказывался от поиска, хотя API поиска доступен. Отсутствие цели среди кандидатов ошибочно принималось за отсутствие в базе.

Относительное напоминание к скрытому сроку JSON не выполнил ни разу: 0/6. Модель не получает результат серверного select обратно и должна была назвать абсолютное время, не зная срока найденной задачи. Здесь требуется изменение контракта: например, декларативное смещение относительно фактического deadline с вычислением на сервере либо отдельный этап чтения. Одна доработка формулировки инструкций не предоставит отсутствующие данные. Для видимого срока результат JSON — 2/6: среди ошибок были вычисления относительно текущего момента вместо дедлайна. Поэтому вычисление на сервере полезно и для видимых задач.

Code Mode правильно вычислил скрытое относительное напоминание в 5/6 проверок и видимое в 6/6: программа может прочитать deadline найденной задачи и вычесть 35 минут. Этого преимущества недостаточно для выбора режима целиком — поиск обычных скрытых задач и смешанные команды работают хуже JSON.

На массовом переносе трёх просроченных дел группы, без изменения четвёртого будущего дела, DIRECT получил 6/6, JSON — 3/6, Code Mode — 4/6. Ошибки JSON включали подмену reschedule на update и пропуск all:true: выборка трёх задач ошибочно обрабатывалась как поиск единственного совпадения. При выборе 21 задачи JSON корректно остановился по лимиту во всех шести проверках. DIRECT не получил зачёта: при 100 задачах предлагал только видимую часть группы; при 200 мог сообщать об отсутствии задач. Применение этих предложений не выполнялось.

Неоднозначное название остаётся отдельным провалом JSON: 0/6. Во всех проверках вместо уточнения предлагалось создание новой задачи. Программа не дошла до серверной проверки неоднозначности, потому что неверно выбрала создание. Одной защиты поискового select здесь недостаточно: до выбора действия нужно надёжнее различать новое дело и изменение существующего.

У DIRECT сценарий create-dates получил 0/6 из-за автоматического назначения группы, не указанной в запросе. Обе задачи и их дедлайны при этом были правильными. Это следствие заранее выбранного строгого критерия отсутствия непрошенных изменений, а не шесть ошибок распознавания дат. В метрике дедлайнов эти времена зачтены. Изменять правила оценки после получения ответов не стали.

JSON остаётся основным направлением дальнейшей доработки, но этот набор не подтверждает готовность заменить DIRECT без ограничений. Приоритеты: серверное вычисление относительных напоминаний; различение create и изменения скрытой задачи; однозначный контракт переноса срока; запрет частичного выполнения массовой команды во всех режимах. Последний пункт касается и текущего DIRECT. После изменений нужны повтор этого набора и прежние 150 реплик, чтобы исправление сложных случаев не испортило обычные команды.

## Расход и воспроизведение

Пилот: 12 измерений и 12 HTTP-вызовов; итоговый прогон: 252 измерения и 263 HTTP-вызова. Всего на этом этапе — 275 из отдельно ограниченных 360 вызовов. Предыдущий цикл сохраняет собственный счётчик 2949/3000; он не сбрасывался и не смешивался с этим этапом. Пилот не входит в итоговые проценты. Ошибок API в обоих прогонах нет, снимки задач и расписаний совпали во всех измерениях.

Код набора зафиксирован коммитом 3b79867 в ветке assistant-plan-vs-code-mode. Отпечаток классов планировщиков совпадает с предыдущим этапом доработки JSON: измеряемые реализации во время этого сравнения не менялись. Стенд и режим по умолчанию не переключались.

Построчные метрики, ранги целей и причины ошибок: [CSV](planning-large-context-measurements.csv). Полные ответы модели и действия находятся локально в core-service/app/build/reports/planning-large-final.json, пилот — planning-large-pilot.json. Эти файлы содержат только синтетические данные, ключи API в них не записываются. Команды запуска и описание проверок приведены в [документации планировщиков](assistant-planning.md#большие-активные-списки).

После живого прогона выполнена обычная регрессия приложения: 171 тест, без ошибок и пропусков. Четыре проверки генератора сводки также прошли. Генератор отклоняет неполные прогоны, дубликаты измерений, несопоставимые наборы режимов и неверный счётчик HTTP-вызовов. CSV независимо сверен с 252 строками исходного отчёта; все снимки базы совпадают.

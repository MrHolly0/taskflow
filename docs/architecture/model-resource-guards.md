# Ограничение ресурсов модели

Реализовано 09.11.2026 в ветке `model-resource-guards` от main. Исходные замечания и места в старом коде сохранены в [разборе](model-resource-protection-review.md). 09.11.2026 проверенная версия объединена с локальной main через fast-forward до `348422e`. Рабочий стенд не обновлялся, push не выполнялся.

## Что теперь ограничено

Обработка ассистента создаёт контекст с владельцем и общим дедлайном. Он проходит через HTTP в nlp-worker вместе с отдельным внутренним секретом. Worker проверяет секрет до разбора тела и допуска к работе. UUID и дедлайн из публичных заголовков пользователя не используются: core формирует внутренние заголовки сам. Ручные операции с задачами не требуют квоты модели.

Для слотов и суточных квот используется общий Redis. Допуск и резервирование выполняются атомарными Lua-скриптами. Ключи имеют префикс `taskflow:resources:{model}:`; число реплик не увеличивает общий предел. Очередь ожидания новых модельных запросов не добавлена: при занятости возвращается 503. Частота 10 обращений в минуту и API-лимиты сохранены отдельно.

| Предел по умолчанию | Значение | Настройка |
| --- | ---: | --- |
| Общая параллельность ассистента | 4 | MODEL_GLOBAL_CONCURRENT |
| Параллельные операции одного пользователя | 1 | MODEL_USER_CONCURRENT |
| Общая параллельность HTTP worker и внешних вызовов | по 4 в отдельных пулах | MODEL_WORKER_CONCURRENT |
| Токены пользователя за сутки | 250000 | MODEL_USER_DAILY_TOKENS |
| Токены всего сервиса за сутки | 5000000 | MODEL_GLOBAL_DAILY_TOKENS |
| Оплачиваемые секунды ASR пользователя за сутки | 600 | MODEL_USER_DAILY_AUDIO_SECONDS |
| Оплачиваемые секунды ASR сервиса за сутки | 7200 | MODEL_GLOBAL_DAILY_AUDIO_SECONDS |

Это начальные защитные значения, а не результат расчёта тарифов или пропускной способности для ста пользователей. Они передаются обоим контейнерам из Compose. Повышение локального числа реплик не отменяет предел Redis. Существующий локальный ограничитель core также остаётся: на одном экземпляре по умолчанию максимум четыре операции.

## Время и память

Дедлайн операции по умолчанию — 35 секунд, один внешний HTTP-вызов — не более 12 секунд и остатка общего времени. Fallback и исправление плана не получают новый полный бюджет. Транспорт ограничивает ожидание всего ответа, включая тело: медленная выдача отдельных байтов не продлевает срок. Ответ внешнего API и worker ограничен 2 MiB. После таймаута запрос на нашей стороне отменяется. Слот внешнего вызова удерживается в worker, а не только в core.

Слоты имеют уникального владельца и lease 60 секунд; позднее освобождение старого владельца не удаляет новый слот. При запуске проверяется, что lease больше суммы общего и внешнего таймаутов. При отказе Redis новое платное действие не начинается. Подключение и команда Redis ограничены 500 мс. Значения времени задаются через `app.resources`, заменив старые независимые настройки 20/30 секунд.

Текст ограничен 8000 символами, сериализованный контекст модели — 64000 байт, выход — 3000 токенами во всех режимах, включая DIRECT и Code Mode. Файл ограничен 16000000 байт на сервисном входе; multipart-ограничения core и worker составляют 16/18 MB. На веб-маршруте файл читается в byte[] после допуска к ассистенту.

Перед ASR аудио декодируется в PCM 16 kHz mono, проверяется фактическая длительность и формируется WAV. Максимум — 120 секунд, минимум — 0,01 секунды. Для сжатых форматов FFmpeg получает только входной pipe через ограниченный cache-протокол; сетевые и произвольные файловые протоколы не разрешены. Декодирование ограничено пятью секундами и остатком дедлайна. Cache нужен для форматов с поиском внутри контейнера, например M4A. Пустая или слишком длинная расшифровка не уходит в модель; пустой результат сбоя ASR не кэшируется.

## Как учитывается расход

Перед каждым обращением к поставщику резервируются суточные токены пользователя и сервиса. Резерв — размер передаваемого UTF-8 JSON в байтах, 4096 единиц на служебное представление и максимальный выход. Это консервативная оценка, а не токенизация точной моделью. После успешного ответа резерв сверяется с prompt_tokens и completion_tokens. Повторная сверка той же резервации не возвращает остаток дважды. Если поставщик сообщил больше резерва, учитывается фактическое значение и срабатывает метрика превышения.

Для ASR резервируются округлённые вверх секунды нормализованного аудио с минимумом 10 на обращение: такой минимальный оплачиваемый объём указан в [документации Groq](https://console.groq.com/docs/speech-to-text). Кэш расшифровки не вызывает ASR повторно. Эти квоты ограничивают токены и оплачиваемую длительность, а не точную сумму в валюте при любых моделях и тарифах.

При сетевом сбое, неизвестном usage или невозможности сверки полный резерв сохраняется. Он не возвращается автоматически после таймаута. Fallback и второй проход получают собственный резерв из оставшейся квоты, а не бесплатную повторную попытку. Суточное окно определяется временем Redis в UTC; Retry-After при исчерпании квоты указывает время до следующего окна. Отказ по квоте доходит до клиента и не превращает реплику в задачу через деградацию. Такие отказы не учитываются circuit breaker как отказ поставщика.

## Повторные запросы

Миграция 045 добавляет владельца и срок владения запросом. Ключ и отпечаток содержимого захватываются короткой транзакцией до ASR и модели. Наличие response_json означает готовый результат; отсутствие ответа при активном владельце — обработку. Повтор с готовым результатом возвращает его без внешней работы. Если запрос ещё выполняется, после допуска возвращается 409; раньше этой проверки может сработать ограничение параллельности с 503. Изменённый вход с тем же ключом после допуска получает 409 до платных вызовов.

Владение действительно 120 секунд. После падения процесса ключ можно захватить по истечении этого срока; новый владелец получает другой UUID. Старый владелец не может сохранить предложение или снять чужое владение. Сохранение предложения и ответа остаётся транзакционным; транзакция не удерживается при ожидании ASR и модели. При обычном исключении владение освобождается без удаления отпечатка входа.

Счётчик частоты стоит до проверки сохранённого ответа, поэтому кэшированный повтор по-прежнему расходует минутный лимит запросов. Запросы без Idempotency-Key не объединяются автоматически по одинаковому тексту: одинаковые слова могут означать две разные команды пользователя.

## Сетевая граница и выкладка

Dev Compose привязывает опубликованные порты БД, Redis, pgAdmin, core и workers к 127.0.0.1. В prod порт nlp-worker не публикуется. Для core и worker требуется одинаковый случайный `NLP_INTERNAL_SECRET` длиной не меньше 32 символов; пример генерации — `openssl rand -hex 32`. Значение не записано в исходный код и не возвращается в ответах. Core и worker нужно обновлять вместе. Ручной запуск worker без корректного секрета останавливается при старте.

Пустой или неверный Telegram webhook-секрет отклоняется до очереди. При настроенных токене бота и публичном URL приложение дополнительно проверяет секрет длиной 32–256 символов. Compose требует непустую переменную. Формат соответствует параметру [secret_token Telegram](https://core.telegram.org/bots/api#setwebhook).

nginx не доверяет всем частным сетям и перезаписывает X-Forwarded-For адресом, который считает доверенным сам. В базовом `infra/nginx/trusted-proxies.conf` real IP выключен. Share-стенд использует шаблон для Tuna: доверяет только явно заданному `TUNA_LOCAL_PROXY_IP` и loopback. На стенде проверено, что Tuna заменяет подставной заголовок и передаёт внешний IP с локальными промежуточными адресами. После настройки nginx передаёт ядру внешний адрес; геопроверка и IP-лимиты различают клиентов туннеля. При смене прокси нужно повторно проверить цепочку и адрес локального входа, см. `infra/README.md`.

## Наблюдаемость

Добавлены занятость слотов по пулу, отказы допуска/квот/Redis, резерв и подтверждённый расход, неподтверждённые расходы, выход за резерв, число и длительность вызовов по поставщику. user_id не попадает в метки Prometheus. Незавершённые обращения с истёкшим владением подсчитываются раз в минуту по частичному индексу. Добавлены четыре правила оповещения: отказ хранилища ограничений, неизвестный расход, превышение резерва и зависшие владения.

## Проверки и границы результата

Полный `./gradlew test --max-workers=2` прошёл: в актуальных JUnit-отчётах 1093 теста, 0 ошибок, отказов и пропусков. Неизменённые модули использовали актуальный кэш Gradle. Выполнена сборка bootJar worker; в упакованном YAML проверены multipart-ограничения и таймаут Redis.

Проверка собранного JAR в Linux-контейнере с FFmpeg прошла все семь групп сценариев из smoke-скрипта, включая M4A с поиском внутри контейнера и multipart больше 1 MB. Подставной API получил три ASR и два модельных обращения (одно намеренно завершилось 503); запрещённые обращения до него не дошли. Все контейнеры, работавшие до smoke-прогона, остались запущены после него. Проверены оба Compose-файла, синтаксис nginx и 11 правил Prometheus. Реальные поставщики не вызывались: счётчик Groq остался 2984/3000.

Проверки выполнялись с синтетическими данными, локальными PostgreSQL/Redis и подставным HTTP API. Они включают одновременное резервирование, общий предел двух экземпляров, долю одного пользователя, повторную сверку, неизвестный usage, истёкшего владельца и отказ хранилища. На настоящем PostgreSQL два одинаковых одновременных голосовых обращения запускают одну расшифровку и один цикл планирования; сохранённый ответ возвращается повторно. Отдельно проверяются HTTP-заголовки, медленное тело ответа и выход за его допустимый размер.

`scripts/check-model-resources.py --image <собранный-worker>` поднимает только собственные временные Redis, подставной API и worker в отдельной сети. Проверяет WAV/Ogg/M4A, длительность, квоты, отказ Redis, общий дедлайн и выходной предел. В конце удаляет только созданные им контейнеры по сохранённым идентификаторам. Подставной API не использует настоящие ключи и не обращается к поставщикам. Сборка для проверки должна включать FFmpeg из Dockerfile worker.

Пределы Lua рассчитаны на используемый Redis 7 без вытеснения ключей и с AOF. При потере данных Redis строгий учёт прошлых расходов гарантировать нельзя: требуется восстановление состояния, а для более жёстких финансовых требований — долговечный журнал и ограничение на стороне поставщика. Дедлайн предполагает согласованные часы узлов. Прерывание HTTP не доказывает прекращение вычислений и списания у внешнего поставщика; поэтому неизвестный расход не обнуляется. Сетевой DDoS, реальный прокси-маршрут Tuna, продолжительная нагрузка ста пользователей и тарифная сумма этого опыта не проверялись.

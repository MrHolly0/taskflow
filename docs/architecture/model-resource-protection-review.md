# Расход модели и защита от перегрузки

Проверка 08.11.2026 после объединения JSON-планировщика с main (`7698a6b`). Основание — приложенный разбор и чтение текущего кода. Запущенные контейнеры, туннели и секреты окружения не менялись; состояние публичного стенда и настройки хостинга этой проверкой не подтверждены. Новых обращений к Groq не выполнялось. Ниже описано текущее поведение и план исправлений, а не результат нагрузочного испытания.

Обновление 09.11.2026: исправления выполнены в отдельной ветке `model-resource-guards`; поведение, проверки и оставшиеся границы описаны в [отчёте об исправлениях](model-resource-guards.md). Ниже сохранён исходный разбор состояния main до этих изменений.

## Что изменилось относительно приложенного разбора

По умолчанию теперь BATCH_PLAN, а не DIRECT: [application.yml](../../core-service/app/src/main/resources/application.yml), строка 72, и оба Compose-файла. Режим может быть переопределён при запуске. JSON получает до 12 кандидатов, включая предварительно подобранные релевантные задачи. Число проходов модели по-прежнему ограничено двумя; валидация плана и конечное применение разделены. Смена режима сама по себе не устраняет замечания по расходам и параллельности.

Лимит «10 в минуту» считает входящие обращения к сервису ассистента, а не отдельные платные вызовы. Одна операция может включать распознавание аудио, два прохода и несколько поставщиков. Повтор с уже сохранённым результатом также проходит admission до проверки кэша.

Размер тела уже ограничен: core допускает файл до 16 MB и multipart-запрос до 18 MB, nginx — тело до 20 M. Проблема в отсутствии отдельного небольшого предела текста и длительности аудио в проверенном маршруте, а не в полностью неограниченной загрузке. Контроллер вызывает `file.getBytes()` до входа в ограниченный сервисный метод; возможна дополнительная память вне четырёх слотов планирования.

## Что уже работает

| Уровень | Предел по умолчанию | Область действия |
| --- | --- | --- |
| nginx `/api/` | 20 запросов/с, burst 40 | IP после обработки real IP |
| nginx изменяющие запросы | дополнительно 5/с, burst 20 | тот же IP |
| Авторизованный API | 300 чтений или 120 изменений/мин | пользователь, Redis |
| Вход в ассистента | 10/мин | пользователь, фиксированная минута в Redis; веб и Telegram |
| Обработка ассистента | 4 одновременных запроса | один экземпляр core, без ожидания свободного слота |
| Подтверждение изменений | 2 одновременных применения | один экземпляр core |

Источники: [nginx](../../infra/nginx/nginx.conf), [API-фильтр](../../core-service/app/src/main/java/ru/taskflow/app/web/ApiRateLimitFilter.java), [частота ассистента](../../core-service/modules/assistant/assistant-impl/src/main/java/ru/taskflow/assistant/application/AssistantRateLimiter.java), [admission](../../core-service/modules/assistant/assistant-impl/src/main/java/ru/taskflow/assistant/application/AssistantAdmissionAspect.java), [применение](../../core-service/modules/assistant/assistant-impl/src/main/java/ru/taskflow/assistant/application/ProposalApplyTransaction.java). Отказ API-фильтра при недоступности Redis — 503; превышение частоты — 429. Отсутствие слота ассистента — 503; отсутствие слота применения — 429 с Retry-After: 5.

Для `/nlp/tool-call` настроена одна HTTP-попытка без автоматического повтора и circuit breaker. Отдельный контур parse/transcribe имеет свои повторы; правило одной попытки нельзя переносить на все маршруты. См. [клиент worker](../../core-service/modules/nlp-gateway/nlp-gateway-impl/src/main/java/ru/taskflow/nlp/infrastructure/NlpWorkerClient.java) и [конфигурацию](../../core-service/app/src/main/resources/application.yml).

Telegram использует сохраняемую очередь с дедупликацией update_id, пределом 1000 ожидающих/обрабатываемых сообщений, шестью попытками и растущей задержкой со случайным разбросом. Веб-вызов модели синхронный. Правила [мониторинга](../../infra/monitoring/alerts.yml) проверяют доступность, ошибки, отставание очередей и ожидание соединений БД; бюджет модели среди них не контролируется.

## Подтверждённые пробелы

### 1. Несогласованные таймауты и неполный предел параллельности

[Core](../../core-service/modules/nlp-gateway/nlp-gateway-impl/src/main/java/ru/taskflow/nlp/infrastructure/NlpGatewayConfig.java) ждёт tool-call до 20 секунд. [Worker](../../nlp-worker/src/main/java/ru/taskflow/nlp/infrastructure/config/ToolCallProviderConfiguration.java) допускает 30 секунд ожидания одного поставщика и последовательный переход к следующему. Общего дедлайна для цепочки нет. После таймаута core освобождает свой слот, хотя внешний вызов worker может продолжаться. Поэтому четыре слота core не означают четыре фактических обращения к поставщикам.

В JSON максимум две попытки, но [ExperimentalAgentLoop](../../core-service/modules/assistant/assistant-impl/src/main/java/ru/taskflow/assistant/application/planning/ExperimentalAgentLoop.java) не ограничивает всю операцию общим временем. Проверка 35 секунд в старом DIRECT перед вторым проходом также не является сквозной отменой. Ограничитель core локальный: несколько реплик получают независимые наборы слотов, один пользователь может занять все слоты экземпляра.

### 2. Повтор защищает результат, но не предотвращает двойные расходы

В [AssistantServiceImpl](../../core-service/modules/assistant/assistant-impl/src/main/java/ru/taskflow/assistant/application/AssistantServiceImpl.java) сначала проверяется сохранённый ответ, затем вызывается планировщик, затем `requestStore.complete`. Для голоса между проверкой и сохранением также выполняется расшифровка. Два одновременных запроса с одинаковым ключом могут оба пройти пустой кэш и потратить ресурсы. Блокировка в [AssistantRequestStore](../../core-service/modules/assistant/assistant-impl/src/main/java/ru/taskflow/assistant/application/AssistantRequestStore.java) выполняется уже после внешней работы.

### 3. Частота запросов не ограничивает стоимость

В проверенном пути нет общего и пользовательского суточного бюджета с резервированием до обращения к внешнему API. Лимит `max_completion_tokens=3000` в [OpenAiCompatibleToolCallProvider](../../nlp-worker/src/main/java/ru/taskflow/nlp/infrastructure/groq/OpenAiCompatibleToolCallProvider.java) задаётся только для JSON-ответа. Подсчёт usage после ответа не заменяет предварительный предел расходов. Ветка fallback существует, однако Groq включён по умолчанию, а ProxyAPI выключен: наличие кода резерва не гарантирует настроенного второго поставщика.

### 4. Сетевые и входные проверки зависят от запуска

[Dev Compose](../../infra/docker-compose.yml) публикует nlp-worker как `${NLP_PORT:-8081}:8081`, без localhost-привязки. При сетевой доступности порта можно обратиться к `/nlp` в обход admission и пользовательских лимитов core. В [prod Compose](../../infra/docker-compose.prod.yml) этот порт не публикуется. Фактическая доступность снаружи зависит от firewall и окружения; здесь она не проверялась.

[TelegramWebhookController](../../core-service/modules/integration-telegram/integration-telegram-impl/src/main/java/ru/taskflow/telegram/infrastructure/web/TelegramWebhookController.java) проверяет секрет только при непустой настройке. Если публичный webhook запущен с пустым секретом, контроллер не проверяет этот заголовок. Наличие секрета в работающем окружении не исследовалось. Telegram поддерживает `secret_token`, передаваемый в `X-Telegram-Bot-Api-Secret-Token`: [документация setWebhook](https://core.telegram.org/bots/api#setwebhook).

nginx доверяет X-Forwarded-For от localhost и всех частных диапазонов RFC1918. Для публичного доступа через туннель нужно проверить, кто формирует и очищает заголовок, и сузить доверие до фактического proxy. Возможность подмены IP в живом Tuna не проверена; утверждать обход лимита по этому признаку пока нельзя.

## Порядок исправлений

1. Закрыть прямой внешний доступ к worker в конфигурации для локальной публичной демонстрации. Для публичного webhook требовать непустой секрет при запуске и проверять заголовок до постановки в очередь. Проверить границу доверенных proxy с Tuna. Другие контейнеры и туннели при этих работах не затрагивать.
2. Ввести общий дедлайн операции, передавать остаток времени в worker, fallback и исправление плана. Ограничить фактические внешние вызовы на стороне worker; новый запрос не должен обходить предел из-за истечения таймаута core. Обрыв соединения не доказывает остановку вычисления и списания у поставщика.
3. Захватывать ключ запроса до ASR и модели: короткая транзакция с состоянием PENDING, отпечатком входа, владельцем и сроком владения. Повтор либо получает готовый ответ, либо статус обработки; другой вход с тем же ключом отклоняется до платной работы. Нужны восстановление после падения и защита от позднего ответа прежнего владельца. Транзакцию БД не держать открытой во время ожидания модели.
4. Добавить атомарное резервирование бюджета на пользователя и сервис до каждого платного шага: ASR, прохода, исправления и fallback. После ответа сверять с usage; неизвестный расход после таймаута не возвращать автоматически целиком, иначе предел можно обходить повторными таймаутами. Ввести явные пределы входного текста, расшифровки, длительности аудио и выхода во всех режимах.
5. Добавить ограничение параллельных работ одного пользователя и общий предел между репликами. Очередь, если потребуется, должна быть ограничена и по размеру, и по времени. При отказе хранилища квот не начинать новый платный вызов. Значения квот выбрать по бюджету и измеренной нагрузке, не выводить их из теста одного аккаунта со 200 задачами.
6. Вывести метрики занятых слотов worker, дедлайнов, повторов, резервов и фактического расхода по поставщикам, очереди и просроченных PENDING. Не помещать user_id в метки Prometheus; пользовательский учёт хранить отдельно.

Разделение частоты и расходов соответствует [OWASP API4:2023](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/): помимо таймаутов, размера загрузки и числа операций требуется ограничивать траты на сторонние сервисы. Эти меры защищают ресурсы приложения; устойчивость внешнего канала при объёмной сетевой атаке отдельно зависит от инфраструктуры провайдера.

## Как принимать исправления

Проверять на локальных заглушках поставщиков без платной нагрузки и без чужих данных:

- Два одновременно пришедших одинаковых ключа запускают одну расшифровку и одну логическую операцию планирования; количество проходов внутри неё остаётся ограниченным. Другой вход с тем же ключом получает конфликт до ASR/LLM.
- Таймаут клиента core не увеличивает число одновременно работающих внешних вызовов выше лимита worker. Fallback и исправление не начинают новый вызов после общего дедлайна.
- Параллельное резервирование не превышает пользовательскую и общую квоты. Расход каждого платного шага учитывается; неизвестное списание после таймаута не создаёт бесплатный повтор.
- Один пользователь не занимает весь сервис. Несколько реплик сохраняют общий предел. Отказ Redis/хранилища лимитов не пропускает платный вызов.
- Worker недоступен через публичный вход в обход core; неверный/отсутствующий webhook-секрет отклоняется до очереди; клиентский X-Forwarded-For не меняет доверенный IP при проверенной цепочке proxy.
- После инфраструктурных изменений повторяются проверки качества планирования, конфликтов и применения. Сравнение 100/200 задач не заменяет отдельный опыт с параллельными пользователями.

Изменения приложения по этому списку пока не вносились. Обучение при первом входе отложено после этих работ: [очередь задач](roadmap.md).

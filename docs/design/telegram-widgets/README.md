# Карточки Мунина в Telegram

Прототип трёх сообщений: напоминание, вопрос об итоге дела и результат разбора голосового. Один HTML-шаблон получает данные через `TelegramWidget.chatData`; отдельная генерация HTML моделью для каждого сообщения не нужна.

`preview.html` показывает карточки со светлой и тёмной темой. Кнопки в предпросмотре работают с демоданными: можно проверить ожидание ответа, успешное действие и ошибку связи. Рабочий бот к прототипу пока не подключён.

Локальный просмотр из корня проекта:

```sh
python3 -m http.server 4182 --bind 127.0.0.1 --directory docs/design/telegram-widgets
```

Открыть http://127.0.0.1:4182/preview.html.

## Проверка в песочнице

Проверено на официальном `TelegramMessenger/widget-sandbox`, commit `eed3271`. Сам фреймворк и его зависимости не включены в проект. `verify.mjs` использует настоящий QuickJS и валидатор профиля; проверяет оба оформления, запросы по нажатию, ошибки, игнорирование устаревшей версии данных и вывод названия как текста.

Из установленной временной копии официального репозитория:

```sh
node --import tsx /path/to/taskflow/docs/design/telegram-widgets/verify.mjs /path/to/widget-sandbox
```

Путь во втором аргументе — та же копия репозитория, из которой запускается команда. Установка нужна только для проверки, в код виджета библиотеки не включаются.

Ограничения Telegram: 32 768 байт HTML, 4096 байт после zlib уровня 9, 1024 байта `chat_data`, не более 600 пикселей высоты. Внутреннего скролла и текстового ввода нет. В карточке нет сетевых обращений при загрузке и таймера опроса. Палитра берётся из темы чата, изображение птицы — из существующего знака Мунина.

## Подключение к боту

Bot API 10.4 добавил `sendWidget`, `widget_query`, `answerWidgetQuery` и `editMessageWidgetData`. Для отправки виджета используется `allow_queries=true`; на стороне бота проверяется владелец задачи или предложения. Действие выполняется существующим сервисом и только после его успешного сохранения обновляется карточка. Ответ на запрос сам по себе состояние сообщения не изменяет.

Состояние содержит `kind`, `key`, `revision`, `title` и до трёх пар `rows`. Для завершённого взаимодействия передаются `terminal`, `heading`, `summary`, `status`. Сохранённый результат запроса имеет вид `{ "ok": true, "state": { ... } }`; отказ — `{ "ok": false, "message": "..." }`. Версия увеличивается сервером. Старое состояние не должно отменить уже показанный новый результат.

Префиксы `eng:<id>:done|working|later` и `p:<shortCode>:a|r` соответствуют действующим сценариям уточнения и предложений. `ntf:<notificationId>:working|later` в примере напоминания — проект нового обработчика, в боте его пока нет. Такой идентификатор должен ссылаться на исходное уведомление и его срок, а не разрешать действие только по произвольному task ID. Карточка после голосового показывает создание одной задачи. Для нескольких действий, редактирования или удаления нужен соответствующий состав карточки и точное число применяемых изменений; до этого используется действующее текстовое предложение. Распознавание голоса и разбор фразы остаются на сервере; пример с 13:00 и 14:20 показывает ожидаемые данные, а не результат нового запуска модели.

Перед подключением нужны новые DTO и маршрутизация `widget_query`, методы клиента Bot API, чтение сохранённых данных для карточки, проверка размера состояния и сквозные тесты действий. Для обычных напоминаний также нужен идентификатор сообщения или напоминания, чтобы кнопка старого сообщения не меняла перенесённое дело.

Внедрение следует сделать переключаемым: обычные текстовые сообщения с inline-кнопками сохраняются. Нельзя надёжно определять поддержку виджетов по версии приложения из обычного webhook — такой версии в текущем событии нет. Нужны явное включение новых карточек и доступный путь обратно; `caption` обеспечивает читаемый текст для старых клиентов, но сам по себе не заменяет их кнопки.

Документация: https://core.telegram.org/bots/widgets и https://core.telegram.org/bots/api#sendwidget.
